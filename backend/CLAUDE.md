# Backend — `backend/` (Serverpod)

Carregado ao trabalhar em `backend/`. Regras gerais do repositório ficam no `CLAUDE.md` da raiz.

### Backend (Serverpod 3.4.13 — Dart workspace)
`backend/` is a Dart workspace with two packages: `sinalacs_server` (the Serverpod server) and `sinalacs_client` (the generated, typed Dart client consumed by the patient and ACS Flutter apps).
```bash
cd backend
dart pub get
dart analyze
cd sinalacs_server
dart test                                          # full suite: unit + integration (the CI job prints the exact count)
dart test test/unit                                # hermetic only, no database needed
dart test test/unit/red_alert_service_test.dart    # single test file
```
Integration tests use Serverpod's `withServerpod` harness, which needs the test database from `sinalacs_server/config/test.yaml` — Postgres on `localhost:9090`, database `sinalacs_test`, user `postgres`, password from the `test:` block of `config/passwords.yaml` (gitignored). The harness applies migrations itself and rolls the database back after each case, so there is **no** manual schema or seed step.

Start that database with the `test` profile of the root compose:

```bash
docker compose --profile test up -d postgres-test
```

It replaced `backend/sinalacs_server/docker-compose.yaml`, the Serverpod template
compose that carried four passwords in cleartext in git and was referenced by
nothing.

Because `config/passwords.yaml` is gitignored, it is missing from any fresh checkout. Locally `scripts/dev/bootstrap_env.sh` generates it; CI generates it in the job. Without it, Serverpod fails while loading config and calls `exit(1)`; since Dart's `exit()` does not flush stdout, the error message is lost and the whole suite dies with exit code 1 and **zero** output. If you ever see that signature, check this file first. The password in it **must** match `TEST_DATABASE_PASSWORD` in `.env` — the bootstrap script keeps them aligned and warns when they drift.

After changing any `.spy.yaml` model or adding an endpoint, regenerate and create a migration (from `backend/sinalacs_server`):
```bash
dart pub global activate serverpod_cli   # once
serverpod generate
serverpod create-migration
```

Run the server directly: `dart run backend/sinalacs_server/bin/main.dart`. Serverpod reads `config/*.yaml` plus `config/passwords.yaml`, and every setting can be overridden by environment variable: `SERVERPOD_DATABASE_HOST`/`_PORT`/`_NAME`/`_USER`/`_PASSWORD`/`_REQUIRE_SSL`, `SERVERPOD_APPLY_MIGRATIONS` (applies migrations at boot — this is what replaced the manual `psql` steps), `SERVERPOD_REDIS_ENABLED` (Redis is optional and off), and `SERVERPOD_INSIGHTS_SERVER_PORT` (remapped to 8083 in `docker-compose.yml`, because Serverpod's default 8081 is the Traefik dashboard here). On the API server specifically, `config/development.yaml` keeps `port: 8080` — the process still listens on cleartext 8080 **inside** the container — while `publicHost`/`publicPort`/`publicScheme` are `localhost`/`443`/`https`. Those three describe the **declared** public address (the encrypted URL Traefik terminates), not the listener and not the address actually in use: no client here reads them, since both apps build the client from `--dart-define`, and the route that would serve them (`AppConfigRoute` in `lib/server.dart`) lives on the webServer (8082), which the compose neither publishes nor routes. And note **which** config file actually serves: the image runs in production mode — the Dockerfile sets `ENV runmode=production` and the entrypoint is `./server --mode=$runmode` — so the running backend reads `config/production.yaml`, not the `development.yaml` quoted above; there, the `apiServer` block keeps Serverpod's placeholder `publicHost: api.examplepod.com` with `publicPort: 443`, `publicScheme: https` and `port: 8080`. The paragraph above is therefore true about the file, but the process in the container does **not** declare `localhost:443` — it declares a hostname nobody resolves. Only Traefik publishes a port for the RPC — `443`, per RNF04/L-08; cleartext 8080 used to be published on the host and no longer is.

MQTT is not part of Serverpod and keeps its own env vars, read by `AppConfig.fromEnvironment()` in `backend/sinalacs_server/lib/src/config/app_config.dart`: `MQTT_BROKER`/`MQTT_USERNAME`/`MQTT_PASSWORD`/`MQTT_USE_TLS`/`MQTT_CA_CERT_PATH`/`MQTT_CLIENT_CERT_PATH`/`MQTT_CLIENT_KEY_PATH` (certificado de cliente do mTLS do broker; só um dos dois definido é erro de boot, e fora de `development` com `MQTT_USE_TLS=true` os dois são obrigatórios), plus `JWT_SECRET`, `AUDIT_CHAIN_SECRET`, `APP_ENV`, `ENABLE_DEV_LOGIN` (default `false` — gates `auth.developmentLogin`, which fails as if the route did not exist when off), `CPF_HASH_PEPPER` (RF01 — the key of the HMAC over the CPF and over the OTP code; the server and the seed writers must share it) and `SMS_GATEWAY` (the OTP delivery channel: it defaults to `log` in `development`, is **required** elsewhere, and `log` — the only gateway implemented today — is refused outside `development` by name, since it sends no SMS at all; the development gateway writes the code to the server log, and nothing else of the signature).

Outside `development`, boot fails fast when `JWT_SECRET`, `AUDIT_CHAIN_SECRET` or `CPF_HASH_PEPPER` is absent, empty, blank, or equal to its own development fallback (`AppConfig.developmentJwtSecret` / `AppConfig.developmentAuditChainSecret` / `AppConfig.developmentCpfHashPepper`) — those fallbacks live in versioned code, so they're public, and `JWT_SECRET` signs tokens that carry role and micro-area, `AUDIT_CHAIN_SECRET` keys the `audit_logs` hash chain while `CPF_HASH_PEPPER` keys the HMAC over the CPF and over the OTP code. They are deliberately independent secrets — rotating one must not affect the others. The shared validation logic is `_resolveSecret`, covered by `test/unit/app_config_test.dart`; `AppConfig.fromMap()` exists so the rules are testable without touching `Platform.environment`.

`REQUIRE_ACS_MFA` (RF07, MFA por TOTP) — ausente, vale `true` em todo ambiente que não seja `development` e `false` em `development` (`AppConfig.resolveRequireAcsMfa`); presente, só a string exata `true` liga. `docker-compose.yml` passa `${REQUIRE_ACS_MFA:-false}` (default só da stack local) e `docker-compose.e2e.yml` fixa `"false"` para a jornada do emulador. Ligada, o ACS sem MFA ativa recebe `MfaEnrollmentRequiredException` no `auth.loginInstitutional` e precisa ativá-la por `auth.beginTotpEnrollment` (matrícula + senha → segredo base32 + URI `otpauth://`, gravado como **pendente**) e `auth.confirmTotpEnrollment` (matrícula + senha + primeiro código); os dois são públicos por desenho (não há token antes da MFA) e contam tentativa errada no mesmo bloqueio do login. Com a MFA ativa, a senha certa sem código recebe `MfaRequiredException` (não conta tentativa); código errado conta; o passo de 30 s aceito vai para `user_credentials.totpLastStep` e o `UPDATE` só deixa o passo avançar, o que barra o replay. TOTP é RFC 6238 (SHA-1, 6 dígitos, 30 s, janela ±1, comparação sem saída antecipada) em `application/auth/totp.dart`. O segredo é cifrado por `HealthCipherTotpVault` com a **mesma** chave dos dados clínicos (`HEALTH_DATA_ENCRYPTION_KEY`): rotacionar ou perder essa chave invalida também as MFAs. **Redefinição (desde a #43):** a coordenação redefine a MFA pela tela do backoffice — `admin.resetAcsMfa` zera as quatro colunas (`totpSecretEncrypted`, `totpKeyVersion`, `totpEnabledAt`, `totpLastStep`) e o ACS ativa de novo na entrada seguinte; ninguém zera coluna à mão desde então. Para o staff é `admin.resetStaffMfa`; a CLI `bin/issue_staff_activation_code.dart` continua sendo o caminho do operador para uma conta que ainda não nasceu (ver "Gestão de contas do backoffice (#43)").

**Staff (backoffice, issue #39).** `auth.loginStaff` (matrícula + senha + `totpCode`), `auth.beginStaffTotpEnrollment` e `auth.confirmStaffTotpEnrollment` são o login institucional do `coordinator`/`admin`: o mesmo `InstitutionalAuthService` do ACS, instanciado com a audiência `staff` (`CredentialAudience`, `staffAuthServiceFor`) sobre `OrmAcsCredentialStore(staff: true)`, que procura a matrícula em `staff_accounts` (`id` = UUID do `users`, `enrollmentId` único, `active`) em vez de `acs`; as duas tabelas têm matrículas independentes e uma matrícula de ACS não existe para o login do staff. A MFA é **sempre obrigatória** para o staff, em todo ambiente (não há `REQUIRE_*_MFA` para ele); conta sem TOTP ativado recebe `MfaEnrollmentRequiredException` e ativa pela tela. O JWT sai com o papel do usuário e **sem microárea**; um papel que não seja `coordinator`/`admin` é recusado depois de a senha conferir e a recusa é auditada. `Authorization.staffRoles` é a regra de papel para os futuros endpoints de staff (os de dados são a issue #40; hoje nenhum os usa). **Sem refresh token para o staff** (JWT de 15 min, depois novo login com código). Staff e ACS seguem a **mesma política** de bloqueio (5 falhas, 15 min dobrando a cada rodada seguinte, até o teto de 24 h; `lockDurationFor`), mas o contador (`failedAttempts`/`lockStreak` em `user_credentials`) é **por conta**: falhas de uma conta não afetam outra (provado em `staff_login_test.dart`); dentro da conta, senha e TOTP compartilham o mesmo contador. As linhas de `audit_logs` distinguem a audiência: o login do staff grava `resourceType: 'staff_session'`; o do ACS, `'session'` (linhas gravadas antes dessa distinção mantêm `'session'`, sem backfill: o login do staff ainda não havia sido lançado; o `actionType` é `login` nos dois, e a ativação da MFA segue a mesma regra, porque todo evento do `InstitutionalAuthService` passa por `_recordAudit`). **Ativação da MFA do staff com código de uso único (issue #48).** `beginStaffTotpEnrollment` e `confirmStaffTotpEnrollment` exigem, além de matrícula e senha, `activationCode`: 130 bits aleatórios, guardados só como SHA-256 em `staff_accounts` (`activationCodeHash`, `activationCodeExpiresAt`, `activationCodeIssuedBy`, `activationCodeIssuedAt`; migração aditiva), validade de 24 h, comparação em tempo constante (`StaffActivationCode`). Código ausente, errado, expirado ou já usado recebe a **mesma** recusa (`Código de ativação inválido ou expirado.`), conta como tentativa falha da conta e grava `denied_staff_activation_code`. A checagem vem **depois** de "a MFA já está ativa", para não revelar que um código existe. `begin` repetido com o mesmo código funciona até a confirmação; só o `confirm` bem-sucedido apaga hash e validade (o último `IssuedBy/At` fica). Emitir de novo invalida o anterior. A ativação do ACS não mudou. **Emissão:** `dart run bin/issue_staff_activation_code.dart MATRICULA --issued-by QUEM [--ttl-hours 24]`, ferramenta de operador com as variáveis `SERVERPOD_DATABASE_*`; mostra o código uma única vez e sai com 2, sem imprimir nada, para matrícula inexistente ou conta inativa. Quem emitiu fica em `activationCodeIssuedBy/At`, **não** em `audit_logs` (a CLI não carrega a cadeia de auditoria do servidor). **A emissão pela interface deixou de ser pendência na #43:** `admin.resetStaffMfa` (só o administrador, nunca a própria conta) zera a MFA e emite o código novo numa transação só, e **essa** emissão entra na trilha (`admin_staff`/`mfa_reset`, com o id do alvo) — é a primeira vez que uma emissão de código de ativação aparece em `audit_logs`. A CLI permanece para o operador e para uma conta que ainda não nasceu; a emissão por ela continua fora da trilha encadeada. O seed de desenvolvimento cria `ADM-001` (`staff_accounts` + `users` com papel `admin`); a senha vem de `DEV_ADMIN_PASSWORD` (obrigatória no `.env`, gerada por `bootstrap_env.sh`; o serviço `acs-credential-seed` do Compose grava o hash Argon2id junto com o do ACS), sem TOTP e **sem código de ativação**: antes do primeiro login, emita um com a CLI acima (nada no seed o cria, de propósito). O seed de e2e (`bin/seed_e2e_fixtures.dart`) cria um admin sintético por execução (bloco `staff` do manifesto, com `activationCode`; matrícula `E2E-ADM-*`; o seed grava só o hash), que o relé `scripts/qa/otp_relay.py` entrega em `/admin` uma única vez; desde a #43 cria também um **coordenador** sintético (`E2E-COORD-*`, bloco `coordinator`, com `staff_accounts."ubsId"` preenchido), entregue em `/coordenador`.

**Leitura do backoffice (`AdminEndpoint`, issue #40).** `admin.indicators`, `admin.microAreas`, `admin.alerts` e `admin.auditLogs`, todos `(Session, {required String accessToken, …})` e somente leitura. O endpoint só verifica o token e delega a `AdminReadService` (`application/admin/`), sobre a interface `AdminReadStore` (`OrmAdminReadStore`, SQL direto com `unsafeQuery` e parâmetros nomeados). Regras, todas cobertas por `test/unit/admin_read_service_test.dart` (10), `test/integration/admin_read_store_test.dart` (14, Postgres real) e `test/integration/admin_endpoint_test.dart` (10, tokens reais):
- **Papel:** só `coordinator` e `admin` (`Authorization.staffRoles`, sem exigir microárea); `acs` e `patient` recebem `AlertPermissionException` mesmo com token válido, e a recusa é auditada (`result: denied`).
- **Escopo (PRD §4.2.2):** o administrador vê o sistema; o coordenador vê só a UBS de `staff_accounts.ubsId` (coluna nova, nula para admin). A #43 entregou a operação escopada por ela, mas **não** a tela para atribuí-la: criar coordenação e escolher a UBS seguem por SQL, e o seed de desenvolvimento não tem coordenador. Coordenador **sem** UBS é recusado em todos os métodos. O filtro de microárea de outra UBS devolve vazio, não fura o escopo. `alerts.microAreaId` é anulável: o administrador conta o alerta sem microárea, o coordenador não o enxerga.
- **Auditoria escopada (issue #43, deferimento da #40).** ~~Só o administrador lê a auditoria~~ — o coordenador lê as linhas cujo **autor** tem microárea na UBS dele (a junção `users` × `micro_areas` que a #40 adiou), e o administrador lê todas. O escopo filtra o **autor** da linha, não o recurso auditado: por isso o coordenador também enxerga as linhas **pseudonimizadas de paciente** da UBS dele (`triage_session`, login OTP), e as linhas de staff (autor sem microárea) ficam invisíveis para ele.
- **Auditoria antes do dado, fail-closed:** cada leitura grava uma linha (`actionType: read`, `resourceType: admin_indicators | admin_micro_areas | admin_alerts | admin_audit_logs`, `result: success`) com `record`, não `recordSafely`: se a linha não grava, a exceção sobe e o store não é chamado. Parâmetro inválido não gera linha de sucesso.
- **TMRAV:** média de `acknowledgedAt − triggeredAt` dos alertas **vermelhos** reconhecidos com `triggeredAt` nos últimos 30 dias, em segundos inteiros; `null` sem amostra (a tela mostra "—", nunca "0s"). O PRD §1.3 não fixa a janela: os 30 dias são decisão desta issue.
- **Paginação:** `limit` de 1 a 100 (padrão 50) e `offset` não negativo; fora disso, `AdminInvalidRequestException` (não é erro de permissão). Alertas por `offset` (`nextOffset` nulo no fim, ordem `triggeredAt` desc e `id` desc); auditoria por keyset (`beforeSequence`, `nextBeforeSequence`), porque o log só cresce e `offset` repetiria linhas.
- **Minimização de PII:** `AdminLabels` — o paciente é `#` + 4 hex finais do UUID (`#A18F`), nunca nome, CPF ou contato; o usuário da auditoria é `MATRÍCULA (Papel)`. `AdminAuditEntry` não tem `ipHash`, `previousHash` nem `entryHash`. O nome do ACS aparece na listagem de microáreas (é profissional, não titular).
- O seed de e2e semeia os 3 alertas do painel só com `E2E_SEED_ADMIN_ALERTS=1` (ligado por `admin_login_e2e.sh`), porque o seed é compartilhado e eles pertencem ao paciente `main`. O seed de desenvolvimento **não** tem coordenador (exigiria nova senha em `.env`): coordenador só existe nos testes — o de e2e é o `E2E-COORD-*`, com `ubsId` preenchido, desde a #43.

**Gestão de contas do backoffice (`AdminEndpoint`, issue #43).** Os oito métodos de escrita e de listagem de contas no mesmo endpoint: `admin.acs` e `admin.staff` (listagem), `admin.createAcs`, `admin.setAcsMicroArea`, `admin.setAcsActive`, `admin.resetAcsPassword`, `admin.resetAcsMfa` e `admin.resetStaffMfa` — todos `(Session, {required String accessToken, …})`, delegando ao `AdminAccountService` (`application/admin/admin_account_service.dart`) sobre a interface `AdminAccountStore` (`OrmAdminAccountStore`). Papel e escopo vêm do `AdminScopeResolver` (`application/admin/admin_scope.dart`), que desde a #43 é a **regra única** do backoffice — o `AdminReadService` também o usa, no lugar da cópia que tinha: só `coordinator`/`admin`; o coordenador opera apenas a UBS de `staff_accounts.ubsId`, fail-closed sem UBS; o administrador, o sistema. Regras, cobertas por `test/unit/admin_scope_test.dart` (8), `test/unit/admin_account_service_test.dart` (43), `test/integration/admin_account_store_test.dart` (28, Postgres real) e `test/integration/admin_endpoint_accounts_test.dart` (18, tokens reais), mais o e2e `scripts/qa/admin_acs_gestao_e2e.sh`:
- **Auditoria fail-closed, sempre com `AuditTrail.record`** (nunca `recordSafely`): recusa grava `denied` **antes** de lançar; leitura audita `read`/`success` antes de consultar o store; escrita bem-sucedida audita **depois do commit**, com `actionType: write`, `resourceType: admin_acs|admin_staff`, `resourceId` do alvo e `result` específico (`created`, `micro_area_changed`, `activated`, `deactivated`, `password_reset`, `mfa_reset`). É o que faz a emissão do código de ativação deixar de ser a única sem trilha.
- **Recusas uniformes:** "não existe" e "não é da sua UBS" devolvem a **mesma** mensagem (`ACS não encontrado.` / `Microárea não encontrada.` / `Conta de equipe não encontrada.`), para o coordenador não descobrir, por tentativa, o que existe fora da UBS dele. Erro de permissão continua `AlertPermissionException` com `acesso restrito ao backoffice`; as validações de entrada devolvem `AdminInvalidRequestException` com texto sobre a própria entrada do operador.
- **`createAcs`:** a UBS **nunca** vem do pedido — sai da microárea escolhida (é o único dado que o escopo do coordenador pode comparar). `users` (papel `acs`), `acs` e `user_credentials` numa única transação; a corrida que passa pela pré-checagem de matrícula é fechada pelo índice único do banco, e o `insertAcs` devolvendo `null` cai na mesma mensagem, nunca em erro de servidor. A **senha inicial é sorteada pelo servidor** (`AcsInitialPassword`: 16 caracteres de um alfabeto de 31 símbolos, sem os pares ambíguos `0`/`O` e `1`/`I`/`L`, em grupos de quatro, ~79 bits — o doc de classe fala em 30; o alfabeto tem 31), mostrada uma única vez e nunca guardada — só o hash Argon2id vai para `user_credentials`. O `cpfHash` do ACS criado é um placeholder aleatório (`acs-sem-cpf-<uuid>`) e o `birthDate` um sentinela (1900-01-01 UTC): nunca um CPF/HMAC real, pela armadilha de `spec/lgpd_data_audit.md` L254 (o login passwordless emite papel de *paciente*).
- **`setAcsMicroArea`:** grava `users."microAreaId"` e `acs."ubsId"` numa transação, com o predicado do escopo **dentro** do `WHERE` (a checagem e a escrita não são duas decisões sobre estados diferentes); devolve a linha relida do banco. O JWT em curso do ACS continua com o território antigo até o refresh — a microárea do token novo é relida do banco a cada `refreshSession`.
- **`setAcsActive`:** desativar revoga, **na mesma transação**, todas as famílias de refresh token e todos os tokens de envio diferido da conta: não existe instante observável em que o ACS esteja inativo e ainda com sessão viva. Reativar não ressuscita token nenhum — o acesso novo se obtém com login (senha + TOTP). Idempotente (desativar um já inativo conclui e audita de novo: o que a trilha registra é o pedido do operador).
- **`resetAcsPassword`:** senha nova sorteada pelo servidor (mesmo gerador), mostrada uma única vez. A escrita é o `saveCredential` que já existia, e é ele que **zera o bloqueio** (`failedAttempts`/`lockedUntil`/`lockStreak`): a senha nova não tem relação com as tentativas da antiga. As sessões em curso **não** são revogadas (decisão do plano): cortar o acesso na hora é a desativação.
- **`resetAcsMfa`:** apaga o segredo TOTP e o estado da ativação, para o ACS ativar de novo na entrada seguinte — é o caminho que a recusa "Peça a redefinição à coordenação" não tinha. A senha e o bloqueio **não** são tocados (redefinir a MFA não é desbloquear a conta). Idempotente.
- **`resetStaffMfa`:** só o administrador, e **nunca a própria conta** (a recusa compara ids **canônicos**, em minúsculas, porque o `UuidValue` e o `::uuid` aceitam a mesma conta grafada em maiúsculas). Zera as quatro colunas `totp*` **e** emite o código de ativação novo numa transação só, devolvendo-o uma única vez (`activationCodeIssuedBy` = o ator; `activationCodeHash` = SHA-256; validade de 24 h). Conta inexistente e conta inativa recebem a mesma mensagem.
- **Sem migração:** só modelos de API (`AdminAcs`, `AdminStaff`, `AdminAcsCreationResult`, `AdminPasswordResetResult`, `AdminStaffMfaResetResult`). **Aberto, nomeado:** criar coordenação e atribuir `ubsId` pela tela não existe; a troca de senha pelo próprio ACS não existe; os resets validam o alvo por leitura e escrevem por PK (TOCTOU residual); `enrollmentIdTaken` é global, não por UBS (oráculo de existência de matrícula entre UBS).

The dev seed (`sinalacs_server/lib/src/infrastructure/database/seeds/development.sql`) is not optional for a running stack: `auth.developmentLogin` issues tokens for fixed UUIDs, and `alerts.patientId` has a foreign key to `patients` — without the seed, `alerts.createRedAlert` fails with a foreign-key violation. In `docker-compose.yml` the `database-seed` service applies it after the server is healthy.

The seed runs in **four** steps. `development.sql` is plain SQL over `psql`, so it cannot produce the AES-256-GCM value that `patients.chronicConditionsEncrypted` now holds (Track E, RNF03/INV-04): it inserts the rows with an empty ciphertext, and the `health-data-seed` compose service then runs `bin/seed_health_data.dart`, which reuses `HealthDataCipher` to fill those columns. That service reuses the server image (`sinalacs/server:local`) precisely so both processes derive the key from the same `HEALTH_DATA_ENCRYPTION_KEY`. Pasting a fixed ciphertext into the `.sql` was the alternative, and was rejected because it duplicates the encryption logic outside Dart and breaks silently on any key or algorithm change. The third step is `acs-credential-seed` (RF07): `bin/seed_acs_credentials.dart` derives the Argon2id hash and writes the `user_credentials` row of the seeded ACS, for exactly the same reason — Postgres cannot derive Argon2id either — and a literal hash in the `.sql` was rejected by the same argument. It reuses the server image too, refuses to run unless `APP_ENV=development`, and takes the password from `DEV_ACS_PASSWORD`, which `bootstrap_env.sh` generates per machine and which is never versioned. The fourth step is `cpf-hash-seed` (RF01): `bin/seed_cpf_hashes.dart` computes the HMAC-SHA-256 of each seeded patient's CPF with `CPF_HASH_PEPPER` and writes `users.cpfHash` — the same argument once more, and this time the consequence is a login, not a field: the passwordless login looks the CPF up *by hash*, and `development.sql` **still writes a literal there** (`'development-patient'`, and one per seeded patient — lines ~19-30) that matches nothing, so without this step no seeded patient can log in. Who replaces those literals is the `UPDATE` of this step, on the patient rows only; the `.sql` keeps writing them, which is why anyone checking the file finds them and has to keep reading to find the fix. It reuses the server image as well, and the pepper **must** be the same value the server process gets, or no seeded CPF is ever found. The seeded ACS is deliberately left out of it: `verifyOtp` always issues `role: UserRole.patient`, so a CPF on the ACS row would let the passwordless login mint a *patient* token carrying the ACS's id and micro-area.

`HEALTH_DATA_ENCRYPTION_KEY` follows the same `_resolveSecret` rule as the other three secrets, with one extra constraint enforced at boot by `AppConfig._resolveHealthDataEncryptionKey`: it **must be 64 hex characters** (`openssl rand -hex 32`), because `HealthDataCipher` decodes it byte by byte into an AES-256 key. A malformed key used to boot fine and only break on the first write — which `TriageSessionService` swallows by design (classifying risk must not depend on the disk), so triage kept answering the patient while nothing was persisted and nothing was visibly wrong. `AppConfig.developmentHealthDataEncryptionKey` is therefore a hex literal, not a phrase like the other three development fallbacks — an earlier non-hex literal made the first `encrypt()` in development throw `FormatException`.

Each encrypted column stores a `keyVersion` next to the ciphertext, but **nothing reads it back**: `HealthDataCipher.decrypt` always uses the one key the process was configured with. The column is a marker for a future rewrite routine; until that routine exists, changing `HEALTH_DATA_ENCRYPTION_KEY` makes every previously encrypted row unreadable (GCM authentication failure). Real key rotation is a future production improvement, not an MVP requirement.

The three clinical columns are encrypted at the ORM boundary only: `OrmPatientDirectoryStore`, `OrmTriageSessionStore` and `OrmVisitStore` take a `HealthDataCipher` and translate to/from the plaintext types (`PatientDirectoryEntry`, `TriageSessionRecord`, `VisitRecord`) that `application/` works with. Keep it that way — a service that decides whether to encrypt is the failure mode this design exists to prevent.


### Backend (`backend/`) — Serverpod workspace
`backend/` is a Dart workspace with `sinalacs_server` (the server) and `sinalacs_client` (the generated typed client). Serverpod was the original stack decision recorded in `spec/stack.md`/`spec/PRD_system.md`; it was not implemented at first — the server was a hand-rolled `dart:io` HttpServer — and was adopted later, replacing it. The Dockerfile (`backend/sinalacs_server/Dockerfile`) is a multi-stage build: `dart compile exe` (AOT) on `dart:3.12.2` (bumped from `3.8.0` because the `postgres` package, a transitive/direct dependency, requires `sdk: '^3.9.0'`), copied into `alpine` with a non-root user, `curl` for the healthcheck, and a `HEALTHCHECK` that does `POST /health/check`.

Layering under `backend/sinalacs_server/lib/src/`:
- `models/` — the schema as `.spy.yaml` model files: 21 tables, 9 enums (`RiskLevel`, `AlertStatus`, `SyncStatus`, `UserRole`, `ConsentPurpose`, `ArrivalMethod`, `DataSubjectRequestType`, `DataSubjectRequestStatus`, `VisitAuthorship`), typed exceptions, and endpoint result types. `serverpod generate` turns these into Dart classes shared by server and client; `serverpod create-migration` turns them into SQL under `migrations/`.
- `application/` — use-case services, unchanged by the migration: `alerts/red_alert_service.dart` (red alert creation/ack, idempotency, micro-area/role enforcement), `triage/triage_engine.dart` (deterministic symptom → `RiskLevel`, mirrors Manchester Protocol logic), `sync/sync_fsm.dart` (`idle → localWrite → queued → syncing → {synced|conflict|error}`), `auth/development_auth_service.dart` (dev-only HMAC tokens, **not** real institutional auth).
- `infrastructure/` — `database/orm_alert_store.dart` (implements `AlertStore` over the Serverpod ORM), `database/seeds/development.sql`, `mqtt/mqtt_alert_dispatcher.dart` (implements `AlertPublisher`, publishes/subscribes per micro-area topic, handles ACK payloads).
- `endpoints/` — the RPC surface. `runtime/alert_runtime.dart` holds process-scoped state (MQTT dispatcher, config), because endpoints are constructed per request.
- `config/app_config.dart` — MQTT and auth env vars. Database and server settings come from Serverpod's `config/*.yaml`.

Never hand-edit anything under `lib/src/generated/` or `migrations/` — run `serverpod generate` / `serverpod create-migration` instead.

Key pattern: application services depend on abstract interfaces (`AlertPublisher`, `AlertStore`) defined alongside them in `application/`, implemented by `infrastructure/`. Follow this when adding new use cases — keep `application/` testable without real Postgres/MQTT (see how `test/unit/red_alert_service_test.dart` fakes both).

**Serverpod is RPC, not REST**, so there are no URL routes to match: the generated client calls methods. Toda decisão de papel e de presença de território no token passa por uma regra
única, `Authorization.require` (`lib/src/application/auth/authorization.dart`): o
chamador decide o que lançar (`StateError` nos serviços territoriais,
`TriageAuthorizationException` na triagem), e é isso que preserva a tradução
`StateError → AlertPermissionException` feita nos endpoints. A comparação entre a
microárea **do paciente** e a do ACS **não** passa por ela e continua inline em
cada caso de uso (`onboarding_service.dart:112-113`,
`visit_sync_service.dart:252-262`), porque a guarda nunca vê o paciente. Os endpoints com postura integralmente autenticada estendem `AuthenticatedEndpoint` (`lib/src/endpoints/authenticated_endpoint.dart`), que centraliza a verificação do token; `test/unit/endpoint_auth_posture_test.dart` lê o texto-fonte de `lib/src/endpoints/` e falha se um endpoint novo não estender a base nem constar da allowlist justificada. `requireLogin` continua `false` em todos: o `AuthenticationHandler` do Serverpod não está conectado.
