# Backend — `backend/` (Serverpod)

Carregado ao trabalhar em `backend/`. Regras gerais do repositório ficam no `CLAUDE.md` da raiz.

### Backend (Serverpod 3.4.13 — Dart workspace)
`backend/` is a Dart workspace with two packages: `sinalacs_server` (the Serverpod server) and `sinalacs_client` (the generated, typed Dart client consumed by the patient and ACS Flutter apps).
```bash
cd backend
dart pub get
dart analyze
cd sinalacs_server
dart test                                          # full suite: unit + integration (the CI job prints the exact count)
dart test test/unit                                # hermetic only, no database needed
dart test test/unit/red_alert_service_test.dart    # single test file
```
Integration tests use Serverpod's `withServerpod` harness, which needs the test database from `sinalacs_server/config/test.yaml` — Postgres on `localhost:9090`, database `sinalacs_test`, user `postgres`, password from the `test:` block of `config/passwords.yaml` (gitignored). The harness applies migrations itself and rolls the database back after each case, so there is **no** manual schema or seed step.

Start that database with the `test` profile of the root compose:

```bash
docker compose --profile test up -d postgres-test
```

It replaced `backend/sinalacs_server/docker-compose.yaml`, the Serverpod template
compose that carried four passwords in cleartext in git and was referenced by
nothing.

Because `config/passwords.yaml` is gitignored, it is missing from any fresh checkout. Locally `scripts/dev/bootstrap_env.sh` generates it; CI generates it in the job. Without it, Serverpod fails while loading config and calls `exit(1)`; since Dart's `exit()` does not flush stdout, the error message is lost and the whole suite dies with exit code 1 and **zero** output. If you ever see that signature, check this file first. The password in it **must** match `TEST_DATABASE_PASSWORD` in `.env` — the bootstrap script keeps them aligned and warns when they drift.

After changing any `.spy.yaml` model or adding an endpoint, regenerate and create a migration (from `backend/sinalacs_server`):
```bash
dart pub global activate serverpod_cli   # once
serverpod generate
serverpod create-migration
```

Run the server directly: `dart run backend/sinalacs_server/bin/main.dart`. Serverpod reads `config/*.yaml` plus `config/passwords.yaml`, and every setting can be overridden by environment variable: `SERVERPOD_DATABASE_HOST`/`_PORT`/`_NAME`/`_USER`/`_PASSWORD`/`_REQUIRE_SSL`, `SERVERPOD_APPLY_MIGRATIONS` (applies migrations at boot — this is what replaced the manual `psql` steps), `SERVERPOD_REDIS_ENABLED` (Redis is optional and off), and `SERVERPOD_INSIGHTS_SERVER_PORT` (remapped to 8083 in `docker-compose.yml`, because Serverpod's default 8081 is the Traefik dashboard here). On the API server specifically, `config/development.yaml` keeps `port: 8080` — the process still listens on cleartext 8080 **inside** the container — while `publicHost`/`publicPort`/`publicScheme` are `localhost`/`443`/`https`. Those three describe the **declared** public address (the encrypted URL Traefik terminates), not the listener and not the address actually in use: no client here reads them, since both apps build the client from `--dart-define`, and the route that would serve them (`AppConfigRoute` in `lib/server.dart`) lives on the webServer (8082), which the compose neither publishes nor routes. And note **which** config file actually serves: the image runs in production mode — the Dockerfile sets `ENV runmode=production` and the entrypoint is `./server --mode=$runmode` — so the running backend reads `config/production.yaml`, not the `development.yaml` quoted above; there, the `apiServer` block keeps Serverpod's placeholder `publicHost: api.examplepod.com` with `publicPort: 443`, `publicScheme: https` and `port: 8080`. The paragraph above is therefore true about the file, but the process in the container does **not** declare `localhost:443` — it declares a hostname nobody resolves. Only Traefik publishes a port for the RPC — `443`, per RNF04/L-08; cleartext 8080 used to be published on the host and no longer is.

MQTT is not part of Serverpod and keeps its own env vars, read by `AppConfig.fromEnvironment()` in `backend/sinalacs_server/lib/src/config/app_config.dart`: `MQTT_BROKER`/`MQTT_USERNAME`/`MQTT_PASSWORD`/`MQTT_USE_TLS`/`MQTT_CA_CERT_PATH`/`MQTT_CLIENT_CERT_PATH`/`MQTT_CLIENT_KEY_PATH` (certificado de cliente do mTLS do broker; só um dos dois definido é erro de boot, e fora de `development` com `MQTT_USE_TLS=true` os dois são obrigatórios), plus `JWT_SECRET`, `AUDIT_CHAIN_SECRET`, `APP_ENV`, `ENABLE_DEV_LOGIN` (default `false` — gates `auth.developmentLogin`, which fails as if the route did not exist when off), `CPF_HASH_PEPPER` (RF01 — the key of the HMAC over the CPF and over the OTP code; the server and the seed writers must share it) and `SMS_GATEWAY` (the OTP delivery channel: it defaults to `log` in `development`, is **required** elsewhere, and `log` — the only gateway implemented today — is refused outside `development` by name, since it sends no SMS at all; the development gateway writes the code to the server log, and nothing else of the signature).

Outside `development`, boot fails fast when `JWT_SECRET`, `AUDIT_CHAIN_SECRET` or `CPF_HASH_PEPPER` is absent, empty, blank, or equal to its own development fallback (`AppConfig.developmentJwtSecret` / `AppConfig.developmentAuditChainSecret` / `AppConfig.developmentCpfHashPepper`) — those fallbacks live in versioned code, so they're public, and `JWT_SECRET` signs tokens that carry role and micro-area, `AUDIT_CHAIN_SECRET` keys the `audit_logs` hash chain while `CPF_HASH_PEPPER` keys the HMAC over the CPF and over the OTP code. They are deliberately independent secrets — rotating one must not affect the others. The shared validation logic is `_resolveSecret`, covered by `test/unit/app_config_test.dart`; `AppConfig.fromMap()` exists so the rules are testable without touching `Platform.environment`.

`REQUIRE_ACS_MFA` (RF07, MFA por TOTP) — ausente, vale `true` em todo ambiente que não seja `development` e `false` em `development` (`AppConfig.resolveRequireAcsMfa`); presente, só a string exata `true` liga. `docker-compose.yml` passa `${REQUIRE_ACS_MFA:-false}` (default só da stack local) e `docker-compose.e2e.yml` fixa `"false"` para a jornada do emulador. Ligada, o ACS sem MFA ativa recebe `MfaEnrollmentRequiredException` no `auth.loginInstitutional` e precisa ativá-la por `auth.beginTotpEnrollment` (matrícula + senha → segredo base32 + URI `otpauth://`, gravado como **pendente**) e `auth.confirmTotpEnrollment` (matrícula + senha + primeiro código); os dois são públicos por desenho (não há token antes da MFA) e contam tentativa errada no mesmo bloqueio do login. Com a MFA ativa, a senha certa sem código recebe `MfaRequiredException` (não conta tentativa); código errado conta; o passo de 30 s aceito vai para `user_credentials.totpLastStep` e o `UPDATE` só deixa o passo avançar, o que barra o replay. TOTP é RFC 6238 (SHA-1, 6 dígitos, 30 s, janela ±1, comparação sem saída antecipada) em `application/auth/totp.dart`. O segredo é cifrado por `HealthCipherTotpVault` com a **mesma** chave dos dados clínicos (`HEALTH_DATA_ENCRYPTION_KEY`): rotacionar ou perder essa chave invalida também as MFAs. Não há redefinição pela coordenação ainda: para redefinir a MFA de um ACS, zere as quatro colunas (`totpSecretEncrypted`, `totpKeyVersion`, `totpEnabledAt`, `totpLastStep`) da linha dele em `user_credentials`.

The dev seed (`sinalacs_server/lib/src/infrastructure/database/seeds/development.sql`) is not optional for a running stack: `auth.developmentLogin` issues tokens for fixed UUIDs, and `alerts.patientId` has a foreign key to `patients` — without the seed, `alerts.createRedAlert` fails with a foreign-key violation. In `docker-compose.yml` the `database-seed` service applies it after the server is healthy.

The seed runs in **four** steps. `development.sql` is plain SQL over `psql`, so it cannot produce the AES-256-GCM value that `patients.chronicConditionsEncrypted` now holds (Track E, RNF03/INV-04): it inserts the rows with an empty ciphertext, and the `health-data-seed` compose service then runs `bin/seed_health_data.dart`, which reuses `HealthDataCipher` to fill those columns. That service reuses the server image (`sinalacs/server:local`) precisely so both processes derive the key from the same `HEALTH_DATA_ENCRYPTION_KEY`. Pasting a fixed ciphertext into the `.sql` was the alternative, and was rejected because it duplicates the encryption logic outside Dart and breaks silently on any key or algorithm change. The third step is `acs-credential-seed` (RF07): `bin/seed_acs_credentials.dart` derives the Argon2id hash and writes the `user_credentials` row of the seeded ACS, for exactly the same reason — Postgres cannot derive Argon2id either — and a literal hash in the `.sql` was rejected by the same argument. It reuses the server image too, refuses to run unless `APP_ENV=development`, and takes the password from `DEV_ACS_PASSWORD`, which `bootstrap_env.sh` generates per machine and which is never versioned. The fourth step is `cpf-hash-seed` (RF01): `bin/seed_cpf_hashes.dart` computes the HMAC-SHA-256 of each seeded patient's CPF with `CPF_HASH_PEPPER` and writes `users.cpfHash` — the same argument once more, and this time the consequence is a login, not a field: the passwordless login looks the CPF up *by hash*, and `development.sql` **still writes a literal there** (`'development-patient'`, and one per seeded patient — lines ~19-30) that matches nothing, so without this step no seeded patient can log in. Who replaces those literals is the `UPDATE` of this step, on the patient rows only; the `.sql` keeps writing them, which is why anyone checking the file finds them and has to keep reading to find the fix. It reuses the server image as well, and the pepper **must** be the same value the server process gets, or no seeded CPF is ever found. The seeded ACS is deliberately left out of it: `verifyOtp` always issues `role: UserRole.patient`, so a CPF on the ACS row would let the passwordless login mint a *patient* token carrying the ACS's id and micro-area.

`HEALTH_DATA_ENCRYPTION_KEY` follows the same `_resolveSecret` rule as the other three secrets, with one extra constraint enforced at boot by `AppConfig._resolveHealthDataEncryptionKey`: it **must be 64 hex characters** (`openssl rand -hex 32`), because `HealthDataCipher` decodes it byte by byte into an AES-256 key. A malformed key used to boot fine and only break on the first write — which `TriageSessionService` swallows by design (classifying risk must not depend on the disk), so triage kept answering the patient while nothing was persisted and nothing was visibly wrong. `AppConfig.developmentHealthDataEncryptionKey` is therefore a hex literal, not a phrase like the other three development fallbacks — an earlier non-hex literal made the first `encrypt()` in development throw `FormatException`.

Each encrypted column stores a `keyVersion` next to the ciphertext, but **nothing reads it back**: `HealthDataCipher.decrypt` always uses the one key the process was configured with. The column is a marker for a future rewrite routine; until that routine exists, changing `HEALTH_DATA_ENCRYPTION_KEY` makes every previously encrypted row unreadable (GCM authentication failure). Real key rotation is a future production improvement, not an MVP requirement.

The three clinical columns are encrypted at the ORM boundary only: `OrmPatientDirectoryStore`, `OrmTriageSessionStore` and `OrmVisitStore` take a `HealthDataCipher` and translate to/from the plaintext types (`PatientDirectoryEntry`, `TriageSessionRecord`, `VisitRecord`) that `application/` works with. Keep it that way — a service that decides whether to encrypt is the failure mode this design exists to prevent.


### Backend (`backend/`) — Serverpod workspace
`backend/` is a Dart workspace with `sinalacs_server` (the server) and `sinalacs_client` (the generated typed client). Serverpod was the original stack decision recorded in `spec/stack.md`/`spec/PRD_system.md`; it was not implemented at first — the server was a hand-rolled `dart:io` HttpServer — and was adopted later, replacing it. The Dockerfile (`backend/sinalacs_server/Dockerfile`) is a multi-stage build: `dart compile exe` (AOT) on `dart:3.12.2` (bumped from `3.8.0` because the `postgres` package, a transitive/direct dependency, requires `sdk: '^3.9.0'`), copied into `alpine` with a non-root user, `curl` for the healthcheck, and a `HEALTHCHECK` that does `POST /health/check`.

Layering under `backend/sinalacs_server/lib/src/`:
- `models/` — the schema as `.spy.yaml` model files: 20 tables, 9 enums (`RiskLevel`, `AlertStatus`, `SyncStatus`, `UserRole`, `ConsentPurpose`, `ArrivalMethod`, `DataSubjectRequestType`, `DataSubjectRequestStatus`, `VisitAuthorship`), typed exceptions, and endpoint result types. `serverpod generate` turns these into Dart classes shared by server and client; `serverpod create-migration` turns them into SQL under `migrations/`.
- `application/` — use-case services, unchanged by the migration: `alerts/red_alert_service.dart` (red alert creation/ack, idempotency, micro-area/role enforcement), `triage/triage_engine.dart` (deterministic symptom → `RiskLevel`, mirrors Manchester Protocol logic), `sync/sync_fsm.dart` (`idle → localWrite → queued → syncing → {synced|conflict|error}`), `auth/development_auth_service.dart` (dev-only HMAC tokens, **not** real institutional auth).
- `infrastructure/` — `database/orm_alert_store.dart` (implements `AlertStore` over the Serverpod ORM), `database/seeds/development.sql`, `mqtt/mqtt_alert_dispatcher.dart` (implements `AlertPublisher`, publishes/subscribes per micro-area topic, handles ACK payloads).
- `endpoints/` — the RPC surface. `runtime/alert_runtime.dart` holds process-scoped state (MQTT dispatcher, config), because endpoints are constructed per request.
- `config/app_config.dart` — MQTT and auth env vars. Database and server settings come from Serverpod's `config/*.yaml`.

Never hand-edit anything under `lib/src/generated/` or `migrations/` — run `serverpod generate` / `serverpod create-migration` instead.

Key pattern: application services depend on abstract interfaces (`AlertPublisher`, `AlertStore`) defined alongside them in `application/`, implemented by `infrastructure/`. Follow this when adding new use cases — keep `application/` testable without real Postgres/MQTT (see how `test/unit/red_alert_service_test.dart` fakes both).

**Serverpod is RPC, not REST**, so there are no URL routes to match: the generated client calls methods. Endpoints: `health.check` (returns `{status, mqttConnected, dbConnected}`; answers as soon as the server is up, independent of MQTT/DB state), `auth.developmentLogin` (throws `EndpointDisabledException` unless `ENABLE_DEV_LOGIN=true`, preserving the old 404-not-403 semantics), `auth.loginInstitutional` (o login real do ACS, RF07: matrícula + senha verificadas com Argon2id contra `user_credentials`, sem guardar a senha em nenhuma forma — só o hash com seu salt e os parâmetros de custo; bloqueia a conta após 5 tentativas falhas — 15 minutos na primeira rodada e o dobro a cada rodada seguinte sem um login válido no meio, até 24 h (`lockStreak`, `InstitutionalAuthService.lockDurationFor`) —, que é o rate limiting do achado F6 de `spec/security_assessment.md`, e audita cada desfecho em `audit_logs`; matrícula inexistente e senha errada devolvem a mesma mensagem), `auth.refreshSession`/`auth.logout` (o refresh token do ACS, LGPD-RT06; `loginInstitutional` só emite `refreshToken` quando o cliente envia um `deviceId` não-branco — sem ele o resultado traz `refreshToken` nulo e o JWT de 15 minutos segue valendo sozinho. O token guarda-se em `acs_refresh_tokens` **só como hash SHA-256**, com família, aparelho, `rotatedAt`/`revokedAt` — o `deviceId` é o identificador da instalação (UUID aleatório), não uma atestação de hardware: protege contra token vazado sem ele, não contra comprometimento do aparelho; constantes em `RefreshTokenService`: janela ociosa de 2 h (`idleWindow`), teto absoluto de 8 h contado do login por senha + TOTP (`absoluteWindow`; a rotação não o estende) e tolerância de reuso de 30 s (`reuseGrace`, para a resposta perdida em rede: reapresentar o pai dentro dela devolve um filho e audita `refresh_granted_grace`). Reuso fora da tolerância, aparelho diferente, conta inativa ou sem microárea **revogam a família inteira**, e toda recusa devolve a mesma `SessionExpiredException` com a mensagem única `Sessão expirada. Entre novamente.` (sem dizer o motivo). A microárea do JWT novo é relida do banco a cada refresh, nunca copiada do token antigo. A rotação é um INSERT condicional atômico e a revogação da família roda em duas passagens, para que dois refreshes concorrentes não gerem dois filhos vivos. Cada desfecho vira uma linha `session_refresh` em `audit_logs` (`refresh_granted`, `refresh_granted_grace`, `denied_*`). Os dois métodos são públicos por desenho — o token de acesso já venceu quando o primeiro é chamado — e estão na allowlist fina de `endpoint_auth_posture_test.dart`. `logout` revoga a família, audita `logout` e ignora em silêncio um token que não conhece. O login só poda os tokens expirados do próprio usuário: não há limpeza periódica da tabela), `auth.requestOtp`/`auth.verifyOtp` (o login passwordless do paciente, RF01: CPF validado por dígito verificador e hasheado no servidor em `users.cpfHash` com `CPF_HASH_PEPPER`, mais a data de nascimento; código de 6 dígitos, com TTL de 5 minutos, teto de 5 verificações e 60 s entre pedidos, guardado em `otp_challenges` **como HMAC** — o código em claro existe só entre a geração e o envio — e uma linha de auditoria por desfecho. `requestOtp` responde a mesma coisa exista ou não o CPF — mesmo payload, mesmo status, sem linha de desafio e sem SMS na recusa —, mas **não** equaliza o *tempo* de resposta: as lacunas do RF01 estão no `PROGRESS.md`. `verifyOtp` emite a sessão do paciente com `patientSessionLifetime` (**1 hora**, LGPD-RT06) e não com os 15 minutos padrão, que o ACS mantém porque a renovação dele é feita pelo refresh token (abaixo) — o paciente não tem refresh token e um código OTP não pode ser reapresentado; `completeEnrollment` também emite sessão, com `patientSessionLifetime`), `patients.acceptTermsOfUse` (aceite do Termo de Uso e da Política de Privacidade vigentes por quem entrou por OTP sem onboarding, LGPD-RF18; Both methods are public by design for `authenticate(...)` and sit in the allowlist of `endpoint_auth_posture_test.dart`. Still open, by design or deferred (`PROGRESS.md`, section "Fila de visitas por dono e corrida do login"): `visits.sync`/`pull` accept an inactive ACS until the JWT expires (`isActiveAcs` is only checked by `syncLegacy`; `syncDeferred` re-checks it through the token); no database CHECK ties a null `acsId` to `authorship = legacyUnclaimed`; the existing `visits.sync` has no batch cap; a `localId` existence oracle remains, identical to `visits.sync`'s; `uploadToken`/`refreshToken` are plain RPC arguments, so any future argument logging must scrub them, see VAZ-03 in `spec/lgpd_data_audit.md`), and `patients.listMicroArea` (the ACS's routine-visit patient picker; the micro-area comes from the caller's token, never a parameter, and every call is written to `audit_logs`, whose rows are hash-chained — `AuditChain`/`AuditChainVerifier` in `application/audit/`, keyed by `AUDIT_CHAIN_SECRET` — so tampering with a row is detectable even by someone with direct Postgres write access; `bin/audit_chain_check.dart` verifies the chain on demand). `bin/seed_e2e_fixtures.dart` seeds the e2e stack (`docker-compose.e2e.yml`, see `apps/CLAUDE.md`): synthetic UUIDs/CPFs generated per run by `lib/src/infrastructure/testing/e2e_fixtures.dart`, written **only** to the database `sinalacs_e2e` (it refuses any other name and any `APP_ENV` but `development`); `development.sql` and its `*-seed` services stay for the plain development stack. Errors are typed exceptions declared in `.spy.yaml` and serialized to the client, replacing HTTP status codes. MQTT connects in the background after boot (non-blocking) with exponential-backoff auto-reconnect, so the server stays responsive even if the broker is unreachable — this matters on free-tier hosts that sleep/hibernate. Toda decisão de papel e de presença de território no token passa por uma regra
única, `Authorization.require` (`lib/src/application/auth/authorization.dart`): o
chamador decide o que lançar (`StateError` nos serviços territoriais,
`TriageAuthorizationException` na triagem), e é isso que preserva a tradução
`StateError → AlertPermissionException` feita nos endpoints. A comparação entre a
microárea **do paciente** e a do ACS **não** passa por ela e continua inline em
cada caso de uso (`onboarding_service.dart:112-113`,
`visit_sync_service.dart:252-262`), porque a guarda nunca vê o paciente. Os endpoints com postura integralmente autenticada estendem `AuthenticatedEndpoint` (`lib/src/endpoints/authenticated_endpoint.dart`), que centraliza a verificação do token; `test/unit/endpoint_auth_posture_test.dart` lê o texto-fonte de `lib/src/endpoints/` e falha se um endpoint novo não estender a base nem constar da allowlist justificada. `requireLogin` continua `false` em todos: o `AuthenticationHandler` do Serverpod não está conectado.
